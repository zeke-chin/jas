# JAS 部署说明

[返回中文 README](../README.zh.md) · [English](../README.md)

JAS（Jackson's App Sensei）是自托管的 iOS/iPadOS 签名服务：在 NAS 或 Linux
服务器上提供网页，通过 Apple 账号签名、安装 IPA，并在预计到期前自动续签。
服务运行在服务器上，不依赖 iPad 上的 SideStore 能否启动。

本文以 Docker 部署为主，不是上游 README 的逐字翻译。Docker 不是 JAS 的必要
运行条件，但可以统一依赖，并让 NAS 直接拉取 CI 编译好的镜像，无须安装 Rust。

## 使用前须知

- **网页没有内置登录认证。**不要直接映射到公网；HTTP 下的账号输入、配对文件
  上传也没有传输加密。仅在可信网络测试，远程使用需另行配置 VPN 或带认证的 HTTPS。
- **当前上游代码在签名证书满额时可能自动撤销旧证书**，安装和导出 LC 证书均有
  此行为，可能影响同 Apple 账号签名的 SideStore/其他 App。本次 Docker 支持没有
  改动签名策略；不点击 `Revoke Certs` 并不能完全避免此风险。
- 必须使用该设备有效的 **RPPairing** 文件；普通 `idevicepair` 的 lockdown
  配对文件不能替代它。JAS 不需要也不使用 usbmuxd、netmuxd、USB 透传或特权容器。
- Docker 镜像支持 **Linux AMD64（x86_64）和 ARM64**，适用于 N100 等 x86 NAS
  和 ARM64 服务器。同一标签包含两种架构，Compose 自动匹配宿主机。
  Docker Desktop 的网络行为不同，不作为本文 LAN/mDNS 部署环境。
- 端口可连接、配对成功、安装成功和过期恢复是不同阶段。不要用重要 App 验证
  过期恢复，也不要先卸载已有 App；睡眠、重启、VPN 等场景需在自己的设备上实测。

## 1. 先让 GitHub Actions 发布镜像

将新增文件提交、推送到自己的 fork，然后在 GitHub 的 **Actions → Docker →
Run workflow** 手动运行一次；首次使用 fork 的 Actions 可能需要先启用工作流。
也可由 `main` / `master` 上相关文件的推送自动触发。

成功后镜像发布到当前仓库对应的地址，仓库名会自动转换为小写，例如：

```text
ghcr.io/zeke-chin/jas:latest
```

**在你的工作流实际成功前，不要假定该镜像已经存在。**其他人 fork 后需在 `compose.yml`
中把 `image` 改成自己的 `ghcr.io/<owner>/<repo>:latest`。

工作流使用仓库自动提供的 `GITHUB_TOKEN`，不需要把 Apple 账号、配对文件、
`JAS_SECRET_KEY` 或个人 PAT 放入构建 Secrets。它需要 `contents: read` 和
`packages: write`；若组织策略禁止发布包，需要管理员允许。

GHCR 包首次发布后可能是私有的。如果希望 NAS 无登录拉取，请在 **Packages →
对应包 → Package settings** 中确认可见性为 Public。保留私有时，在 NAS 上用
有该包读取权限的凭证执行 `docker login ghcr.io`；不要把凭证写进 Compose。

发布标签：

| 触发条件 | 镜像标签 |
| --- | --- |
| 默认分支构建成功 | `latest`、分支名、`sha-<完整提交 SHA>` |
| 其他允许的分支 / 手动选择分支 | 分支名、`sha-<完整提交 SHA>`，不更新 `latest` |
| `v1.2.3` 形式的版本标签 | `1.2.3`、`1.2`、`sha-<完整提交 SHA>`，不更新 `latest` |
| Pull request | 只构建和测试，不登录 GHCR、不推送镜像 |

## 2. docker-compose 启动

### 准备配置

安装 Docker Engine 和 Docker Compose v2。部署只需 `compose.yml` 和 `jas.toml`：

```bash
mkdir jas && cd jas
wget https://raw.githubusercontent.com/zeke-chin/jas/master/compose.yml \
     https://raw.githubusercontent.com/zeke-chin/jas/master/jas.toml
mkdir -p data && sudo chown 10001:10001 data && sudo chmod 700 data
```

如果目录已经存在，进入已有目录，不要覆盖现有 `jas.toml` 或数据库。
直接编辑目录里的 `jas.toml` 即可。

上面的目录权限命令用于首次准备部署目录；以 root 操作时可去掉 `sudo`。容器
以 UID/GID `10001:10001` 运行，绑定目录不会继承镜像内的权限。如果是迁移已有
数据，先备份，并确认数据库、IPA 和密钥文件也允许该 UID 读写，不要只修改顶层目录。

部署只需维护 `jas.toml`，不需要 `.env`，也不需要填写 `JAS_SECRET_KEY`。
镜像地址固定在 `compose.yml` 的 `image` 字段中。

首次启动时，入口脚本自动生成随机密钥并保存到 **`./data/.jas-secret-key`**，
权限为 `600`。以后启动读取同一个文件，在容器内部传给 JAS，不打印密钥，也不需要
在 Compose 中声明它。**已有数据库但缺少密钥时会拒绝启动，不会自动换新密钥。**
已有部署的迁移方式见下文，不能仅删除旧 `.env` 中的密钥后直接启动。

`jas.toml` 默认监听所有 IPv4 网卡的 3010 端口，不需要填写服务器的具体 IP：

```toml
[server]
bind = "0.0.0.0:3010"
log_level = "info"
```

Compose 将根目录的 `jas.toml` 只读挂载到容器的 `/etc/jas/jas.toml`。
JAS 服务端启动时由 `Config::load()` 读取，路径由镜像内的 `JAS_CONFIG` 指定；
修改配置后需重启容器。

启动后使用 `http://服务器IP:3010` 访问，`0.0.0.0` 是监听地址，不是浏览器访问地址。
**JAS 没有内置网页登录认证，请限制为可信网络访问，不要直接将 3010 端口暴露到公网。**

保留文件中的其他配置段，不要只留下这两行；尤其存储路径应保持为
`/data/jas.db` 和 `/data/ipas`。如需指定发现用的宿主机网卡，可填写
`discovery.mdns_interface = "enp3s0"`；不确定时保留空字符串。

### 拉取并启动

```bash
docker compose pull
docker compose up -d --no-build
docker compose logs -f --tail 100 jas
```

看到监听日志后访问 `http://服务器IP:3010`，例如 `http://192.168.31.140:3010`。
`Ctrl+C` 只退出日志查看，不会停止后台容器。

Compose 使用 Linux `network_mode: host`，便于 mDNS 和设备 TCP 通信，因此没有
`ports:`。需要改端口时修改 `jas.toml` 的 `server.bind`，随后执行：

```bash
docker compose restart jas
```

`restart: unless-stopped` 会在服务异常退出或 Docker/NAS 重启后尝试恢复容器；
手动停止过的容器不会因此自动恢复。容器以 UID/GID `10001:10001` 运行，不需要
以 root 或 `privileged` 运行；`./data` 和 `jas.toml` 必须提前准备好。

### 直接运行 Rust 服务端

在项目根目录执行 `cargo run --features ssr` 或 `cargo leptos watch` 也会读取
根目录 `jas.toml`。该文件的存储路径是容器内的 `/data/...`；本地设置
`JAS_DATA_DIR=data/local` 即可改写到可写目录，不必再复制一份配置。
也可用 `JAS_CONFIG` 指定其他配置文件。

直接运行不会执行 `docker/entrypoint.sh`，也不会自动生成或读取 `.jas-secret-key`。
需自行设置并保存 `JAS_SECRET_KEY`；复用已有数据时必须使用原密钥。
不要把密钥写入受 Git 跟踪的 `jas.toml`。
网页还需要静态资源，日常开发使用 `cargo leptos watch`，完整构建使用
`cargo leptos build --release`；具体前置依赖见 [构建说明](../README.md#building)。

## 3. 注册设备、安装 IPA

### 注册 iPhone / iPad

1. 用支持 RPPairing 导出的工具（例如 iloader）为**这台设备**完成初次配对并导出
   `pairingFile.plist`。初次配对可能需要 USB 和设备上的信任确认；服务器不能绕过它。
2. 确认 NAS 能到达设备 IP；首次测试让设备解锁、亮屏并连接家庭 Wi-Fi。
3. 在网页 **Devices → Register Device by IP** 中填写设备 IP，上传 RPPairing 文件，
   点击 **Register**。看到设备注册成功及设备名称后再继续。

例如设备 IP 是 `192.168.31.150`，NAS 上可先检查 TCP 49152：

```bash
timeout 5 bash -c 'exec 3<>/dev/tcp/192.168.31.150/49152'
echo "退出码：$?"
```

退出码 0 只说明该端口可连接，不证明配对有效。后续还会建立动态端口的隧道，
只放行 49152 并不保证整个安装流程可用。路由器为设备保留 DHCP 地址通常更方便；
VPN 场景需要 NAS 真正能连接设备，单纯让浏览器访问 NAS 网页并不等于反向可达。

### 添加账号并安装

先阅读本文开头的证书撤销风险，再操作：

1. **Accounts → Add Apple ID** 登录账号，按提示完成双重认证。
2. **Devices → Manage → Install IPA**。
3. `Account` 选择账号，`IPA File` 选择 IPA。
4. 保持勾选 **Store IPA for auto-refresh**，否则后续不能自动续签。
5. 点击 **Install**，等待任务完成，再在设备上验证能打开应用。

IPA 由网页上传，部署者不需要手动复制到数据目录中。先安装没有重要数据的测试应用；
`queued` 仅表示排队，不是安装或续签成功。

## 4. 自动续签

在设备的 **Installed Apps** 页面确认 **Auto-Refresh = ON**。
先点一次 **Refresh** 验证手动续签；**Refresh All** 可批量提交符合条件的应用。

`jas.toml` 的默认策略：

```toml
[scheduler]
interval_hours = 2
refresh_window_days = 3
worker_threads = 1
```

- 每 2 小时检查一次，不是每 2 小时无条件重签。
- 根据最后安装/续签时间加 7 天估算到期时间，进入到期前 3 天的窗口后安排刷新。
- 一次处理一个任务，适合性能较弱的 NAS；无需额外 cron，也无需一直打开网页。
- 需要 JAS 正在运行、账号会话有效、配对有效且设备可达。
- `interval_hours` 必须大于 0，`refresh_window_days` 建议为 1–6，
  `worker_threads` 至少为 1。当前程序并未对所有无效配置提供友好校验。

修改文件后重启容器使其生效。网页 **Settings** 中这些参数是只读展示。
应用需要保留在设备上，服务器需要保留 IPA；调度器不会自动接管 SideStore 的
全部现有应用，也不能保证断网、长期关机或失效配对情况下仍能续签。

## 5. 数据、备份与更新

使用 Compose 文件旁的 **`./data` 目录绑定挂载到 `/data`**，不再使用 Docker 命名卷。
启动后的主要文件如下：

```text
compose.yml
jas.toml
data/
  .jas-secret-key          # 自动生成的密钥；不要删除、替换或公开
  jas.db                  # SQLite 数据库，运行时还可能有 -wal / -shm 文件
  ipas/                   # 网页上传并保留的 IPA
```

- 备份需要保留**整个 `./data`（包括隐藏的密钥文件）、`jas.toml` 和部署配置**。
  密钥和数据库位于同一目录，拿到整个目录的人也能拿到密钥；必须限制数据及备份
  的访问权限，不要提交到 Git 或放进公开下载链接。
- 简单的一致性备份应先 `docker compose stop jas`，再备份整个目录，完成后
  `docker compose start jas`。不要仅在线复制 `jas.db` 而遗漏 SQLite WAL。
- `docker compose down` 不会删除宿主机绑定目录，但手动删除 `./data` 会丢失
  数据和密钥。不要用 `down -v` 清理仍在迁移中的旧命名卷。
- 数据库里的 IPA 路径仍使用 `/data/ipas/...`；不要让新旧实例同时操作同一份数据。

### 从旧环境变量 / 命名卷方案迁移

1. 停止旧服务，备份旧数据和原 `JAS_SECRET_KEY`，不要先删除 `.env` 或旧卷。
2. 旧方案若使用命名卷，将完整数据复制到新的 `./data`；若已使用该绑定目录，
   保留原数据。此修改不会自动搬运旧卷中的内容。
3. 若没有 `.jas-secret-key`，用编辑器将**原来的 64 位十六进制密钥值**保存到
   `./data/.jas-secret-key`，文件只写密钥值，不写 `JAS_SECRET_KEY=`。已有密钥文件
   则保留，不要覆盖。确认目录和数据属于 UID/GID `10001:10001`，密钥权限为 `600`。
4. 使用新镜像启动，确认配对及账号可用后再移除旧 `.env` 中的密钥；新 Compose
   不会自动把宿主机 `.env` 的旧密钥传入容器。

入口脚本也支持通过显式传入 `JAS_SECRET_KEY` 导入旧密钥；已有密钥文件与其冲突
时会拒绝启动，而不是覆盖或轮换。通常直接迁移文件更简单。丢失原密钥后生成一个
新密钥不能解密旧账号和配对记录。

更新前备份，再执行：

```bash
docker compose pull
docker compose up -d --no-build
docker compose logs --tail 100 jas
```

更新不需要 NAS 编译。若想锁定版本，将 `compose.yml` 的 `image` 换为带发布版本标签的镜像地址
或 `sha-<提交 SHA>`。旧程序不一定兼容新版本迁移过的数据库，回滚前需评估并保留
升级前备份。

## 6. 自行构建镜像

Dockerfile 编译**当前仓库的源码**，不会重新克隆上游。既打包后端，也打包 JS、
WASM、CSS 等网页资源；运行镜像不包含 Rust 工具链或 Cargo 缓存。

```bash
docker buildx build --platform linux/amd64 --load -t local/jas:test .
```

如需减少内存压力，可限制并发任务数：

```bash
docker buildx build --platform linux/amd64 --load \
  --build-arg BUILD_JOBS=2 -t local/jas:test .
```

默认使用构建环境可见的 CPU 数量，并没有固定限制为两核。然后将 `compose.yml` 中的
`image` 改为 `local/jas:test`，执行：

```bash
docker compose up -d --no-build --pull never
```

在 ARM Mac 上构建 AMD64 需要模拟执行，可能很慢，也可能遇到 QEMU/链接器崩溃。
Dockerfile 仅在 AMD64 上安装 `cargo-leptos` 时禁用 LLD，ARM64 使用默认链接器；
该处理不能保证解决所有模拟兼容问题。
构建 ARM64 时把上述 `--platform` 改为 `linux/arm64`。
建议使用与目标架构一致的机器，或本仓库的原生双架构 CI。

构建工具版本由 Dockerfile 的 `RUST_VERSION`、`CARGO_LEPTOS_VERSION` 固定，升级时
应一起验证后端和 WASM。项目的两次 Cargo 构建传入 `--locked`，SQLx 使用仓库内
`.sqlx/` 离线元数据。修改数据库查询后仍须按项目说明重新生成 SQLx 缓存。

## 7. GitHub Actions 缓存如何工作

新增工作流是 [`.github/workflows/docker.yml`](../.github/workflows/docker.yml)，与
原有多系统二进制工作流独立，不会替换它。两份工作流可能同时运行。

1. **原生构建**：AMD64 使用 `ubuntu-24.04`，ARM64 使用 `ubuntu-24.04-arm`，
   通过矩阵分别构建，不使用 QEMU。Buildx 用于镜像构建、缓存和多架构标签合并，
   使用 Buildx 不代表启用模拟执行。
2. **镜像层缓存**：`cache-from/to: type=gha`，`mode=max` 保留中间构建层，昂贵的
   `cargo-leptos` 安装位于复制源码之前。
3. **Cargo 编译缓存**：Dockerfile 将 registry、Git 依赖、应用 `target` 和辅助工具
   缓存集中在 `/cache`。已安装的 `cargo-leptos` 由镜像层缓存保留，其临时编译目录
   不再占用持久缓存。通过 `actions/cache` 与固定提交的
   `buildkit-cache-dance` 在不同 runner 间恢复/保存这个挂载。
4. **缓存更新**：缓存键包含平台、Dockerfile/Cargo.lock 哈希和提交 SHA；优先匹配
   相同依赖，再回退到同平台旧缓存，由 Cargo 决定哪些产物需要重新编译。
5. **发布前验证**：先校验 Compose 配置，再将根目录的 `jas.toml` 只读挂载到
   测试容器，检查网页、静态资源，以及使用同一绑定目录重建容器后是否复用原密钥，
   无需真实设备或 Apple 账号。各架构通过后推送带运行编号的独立镜像，不进行第二次编译。
   两种架构均成功后才合并发布 `latest` 等多架构标签，并验证 manifest 包含两种架构。
   此检查不验证实际签名或续签。

普通 GHA 镜像层缓存**不会自动导出 BuildKit cache mount**，只写
`RUN --mount=type=cache` 不足以跨 GitHub runner 保留 Cargo 的编译结果。
参考 [Docker 官方缓存说明](https://docs.docker.com/build/ci/github-actions/cache/)。

首次构建、工具链/依赖变化、缓存被 GitHub 淘汰时仍会较慢。Rust 的 `target` 可能
很大，缓存也有存储和传输成本；关注仓库 **Actions → Caches**，不要承诺每次都
会命中或完全免编译。工作流只对构建及部署配置相关路径触发，纯中文文档更新不会触发本
Docker 工作流。默认分支若不是 `main` / `master`，需要调整其分支过滤。

## 8. 常见问题

**拉取镜像提示 denied / manifest unknown**

确认 Docker 工作流已经成功、镜像地址属于自己的 fork、标签正确，以及 GHCR 包
可见性/登录权限。只克隆代码并不会自动产生镜像。

**配置文件不存在 / 容器重启循环**

确认部署目录中存在 `jas.toml`，并创建好 UID/GID `10001:10001` 可写的 `./data`。
Compose 的短格式挂载会将缺失的宿主机路径创建为目录；缺失的 `jas.toml`
可能因此变成目录，自动创建的 `data` 也可能不允许容器用户写入，应提前准备。
若日志提示数据库存在但密钥缺失，需恢复原密钥；不要删除数据库或重新生成密钥来消除报错。查看
`docker compose logs --tail 100 jas`，但不要将
配对文件、密钥或完整账号会话贴到公开 issue。

**网页打不开**

确认浏览器使用服务器的实际 IP，而不是 `0.0.0.0`，并检查宿主机防火墙和端口冲突。
旧部署如果仍配置为 `127.0.0.1:3010`，需手动修改现有 `jas.toml` 的 `server.bind`
并重启；更新示例文件不会覆盖已有配置。host 网络不通过 Compose 的 `ports` 调整端口。

**`RPPairing verification failed / PairVerifyFailed`**

通常表示设备没有接受当前配对身份，但该错误本身不能证明文件过期。确认 IP 和
文件对应同一设备、设备已解锁；iloader 的导出可能复用缓存，必要时备份旧文件后
重新配对再导出。重新配对可能影响其他工具使用的旧 RPPairing 记录。

**`plist did not contain alt_irk`**

该字段用于自动匹配设备 mDNS 信息，缺失会跳过自动 IP 匹配；它不是通过手动 IP
执行配对验证的必需字段。不要手工伪造字段。

**`Keyring and fs storage not enabled ... in-memory storage`**

当前 JAS 在创建底层默认存储时可能打印该警告，随后使用自有 SQLite `DbStorage`
替换它。警告本身不代表 JAS 没有持久化；还应确认 `./data` 挂载和数据库写入正常，
无需仅为这条警告重新编译 `fs-storage`。

**重启或更新后数据像是丢了**

先检查实际绑定的 `./data` 是否仍是原目录，以及隐藏的 `.jas-secret-key` 是否完整，
不要立即重新配对、删除数据或重置密钥。将 Compose 文件移动到其他目录后，相对
路径 `./data` 也会改变；只改项目名不会改变绑定目录。
